# S13 取证:自愈事件的「来源分类」预注册(2026-09-22)

> 只读。不改自愈行为、不改 `app/**`、不换 pin、不动系统配置。结论只到证据能支撑的那一层。

## 一、问题

14 号 S13 记的是「服务**每天自愈 3~8 次**、死因未明」。但本项目有一条例行手册要求:
**改动 `app/**` 必须重启服务**,而推荐的重启手法是
`Stop-Process` 杀掉 8787 持有者 → 删 `watchdog.state` → `schtasks /run /tn "NEW ECO Watchdog"`(03
号手册,2026-09-22 多个步骤都照此执行)。

⇒ 一个尚未排除的可能:**看门狗日志里的"自愈"计数,很大一部分是我们自己的计划性重启**,
而不是服务自己死掉。本轮的目的不是找死因,而是先把**计数本身**拆干净 ——
否则对一个被污染的统计量找生理解释,是把错误的命题当真。

## 三、冻结判据(跑数前在此钉死,跑完后不得因结果改)

- **F0 一次调用** = `watchdog.log` 中带时间戳的记录行;`连续落在同一分钟内`的多行合并为**一次调用**
  (例:14:45:03 不可达 / 14:45:05 已发出拉起 / 14:45:06 宽限成功 = 1 次调用)。
- **F1 分类**:
  - `定时档调用` = 分钟尾数为 **5** 且 **秒 ≤ 9**(依据:计划任务 StartBoundary 09:45 + Repetition `PT10M`,
    实测健康探活几乎全部落在 `HH:x5:01`);
  - `额外调用` = 其余一切(**不是**"定时"的调用,来源待定)。
- **F2 自愈事件** = 当次调用里出现「服务不在 ⇒ 已发出拉起命令」。每次调用至多计 1 次。
- **F3 主统计量**(主判据只算 **未见区间**):
  - 探索集 = **2026-09-22** 当天(已看过的 8 次,驱动本判据的设计,**只报表不作判决**);
  - 确认集 = **2026-09-15 00:00 ~ 2026-09-21 24:00**(未用来设计判据)。
  - 记 `N_s/D_s` = 确认集内定时档调用数 / 其中自愈事件数;`N_x/D_x` = 额外调用数 / 其中自愈事件数。
  - **C1(判决)**:若 `D_x/N_x ≥ 0.5` **且** `D_s/N_s ≤ 0.05` ⇒ 判
    「**自愈计数主要来自非定时的计划性重启**」;否则判「**不能排除自发死亡为主**」。
  - **C2(辅助,不判决)**:确认集内每次额外触发的自愈事件,其 ±10 分钟内是否存在本仓库提交
    (`git log --name-only`);`命中率`只作旁证,不参与 C1。
- **F4 证据上限(先写死)**:本机 `wevtutil gl Microsoft-Windows-TaskScheduler/Operational` = **enabled: false**
  ⇒ **没有任何 OS 级证据**可区分「手动 `schtasks /run`」与「计划任务被延迟启动」。
  因此本次结论**只能到"这些调用不合计划 cadence"这一层**,禁止写成"已证实是手动重启"。
- **F5 不改任何东西**:本轮不启用该日志通道(系统级,需用户拍板)、不调整计划任务、不改判据/阈值。

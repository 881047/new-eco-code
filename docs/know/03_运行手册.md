# 运行手册（无人值守终端）

## 一、服务

- 地址 `http://127.0.0.1:8787`（uvicorn，`app.main:app`）。
  **⚠️ 2026-09-24 更正（本轮排查实踩）：日志有两条通道，别只看一个。**
  - **业务日志 = `logs/app.log`** —— `app/logger.py` 写的，轮转 5 MB × 3。缓存 / 训练 /
    调度 / 告警 / 成交这些**业务行为全在这里**；
  - **uvicorn 访问与错误日志 = `logs/server.log`**（`logs/server.err.log` 同理）—— 那是
    **启动命令的 stdout/stderr 重定向目标**（`start.bat` 与 `service_watchdog.py` 里的
    `>> logs\server.log 2>&1`），**不是 logger 的产物**。
  - 旧版此处只写 `server.log` / `server.err.log` ⇒ 我本轮一度把"`server.log` 里没有缓存日志"
    当成证据，**差点误判**。查业务行为**必须看 `app.log`**。
- **改了 `app/**` 必须重启服务**（无热加载）。顺序（policy 会拦复杂组合命令，**分开执行**）：
  ① 找 pid 并 `Stop-Process -Id <pid> -Force`；
  ② **删掉看门狗的冷却时间戳** `Remove-Item logs\service_watchdog.state`；
  ③ `D:\Python313\python.exe -X utf8 scripts\service_watchdog.py`；
  ④ 探活 `http://127.0.0.1:8787/api/overview`（应 200）。
  ⚠️ **第 ② 步不能省**（2026-09-13 实测踩到）：看门狗有 **5 分钟冷却**（防重启风暴），
  若你在 5 分钟内刚拉起过服务，直接跑它会打印"服务不可达，但 5 分钟冷却中 ⇒ 不重复拉起"
  ⇒ **服务就这样停在线下**（下一次自愈要等 10 分钟档）。删掉 state 文件等价于"人工宣告这次是计划内重启"。
- 找 pid：`Get-CimInstance Win32_Process -Filter "Name='python.exe'" | ? { $_.CommandLine -like '*uvicorn*' }`
- **单实例锁 `data/service.lock` = 运行时文件，不入库**（2026-09-18 审查收口）：`app/main.py`
  的 lifespan 用 `app/filelock.py` 在它上面做互斥，内容 = `pid\n进程创建滴数`，**每次重启都变**。
  acquire 会自己创建（文件不存在是正常初态），所以它既不需要进 git、也不该进 —— 同族的
  `data/.task.lock` 早已在 `.gitignore` 里。它是全仓唯一漏进跟踪的运行时文件（2026-09-18 已
  `git rm --cached` + 补 `.gitignore`）。⚠️ 清理时**只准从索引里摘，不许删磁盘上的那份** ——
  服务正持有它，删了双实例互斥就失效了。

### 三补、终端**自己**的失败告警与抢锁重排（2026-09-14 外部审查 P0-1/P0-2，已修）

**起因（复核为真）**：全项目 `send_ops_alert` 只有 2 个调用点（备份校验、周频核对），而
`scheduler._guarded` 抓到的日链/月链异常**只写日志 + `pipeline_run.status='error'`** ⇒ 无人值守时
"整月没出方案""整周零成交"可以**完全静默**地发生。同时所有档共用一把锁，而退避重排**只有月链**有：
09:32 建仓档 / 18:05 补成交档 / 19:45 判据④核对档被挤掉就是一天（甚至一周）没了。

**修法（不碰任何回测口径，无需换 pin）**：

1. `_guarded` 的异常分支 → `_ops_alert_once()`：发一封「任务失败」运维邮件（正文带 run_date / pid /
   异常一行 / 指向 `pipeline_run`）；**同 key 同一天只发一封**（保鲜档一晚 3 次触发 + 重排会打很多次，
   不去重就会把告警变成噪声）。
2. 抢锁失败 → `_retryable()` 退避重排（间隔按各档有效窗口定，写死在 `scheduler._RETRY_MIN`）：
   `weekly_sleeve` 3/6/12 分钟（重排仍在盘中，今开价全天固定）、`weekly_evening` 10/20/40、
   `daily_summary` 10/20、`weekly_health` 15/30。每次重排先记一行 `status='skipped'`，
   **用尽仍拿不到锁 ⇒ 再发一封告警**（否则还是静默）。重排复用同一执行函数（`__wrapped__` 恒等守卫）。
3. 复发检查：`SELECT stage, status, count(*) FROM pipeline_run WHERE stage IN
   ('weekly_sleeve','weekly_evening','daily_summary','weekly_health') GROUP BY 1,2` ——
   `skipped` 行多 ⇒ 说明有档在被挤；`error` 行 = 已发过告警。
4. 守卫测试：`tests/test_scheduler_ops_alert.py`（**11 条**：失败必告警 / 同日不刷屏 / 跨日重发 /
   告警失败不影响主流程与锁释放 / 成功不告警 / 重排 id 与间隔 / 换下一档间隔 / 用尽告警 /
   名单与档位一一对应 / **正常路径照常执行槽函数** / 执行函数恒等）。
5. ⚠️ **测试隔离**：因为调度器现在会主动发信，`tests/conftest.py` 把邮件出口换成了**只记录、不外发**
   的实现（`_no_send`，不发信也不写 `notify_log`）—— 07 号 #1/#2 那两次"pytest 真发邮件"的事故
   从此在结构上不可能复发。
